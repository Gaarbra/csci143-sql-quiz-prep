Every query here runs on real Postgres and real SQLite, side by side.

His quizzes hand you a query and ask what it prints in sqlite3 and in postgres. This page lets you check your hand-trace on both engines, edit any query, and see where they disagree.

Same data, same query, different output: Postgres sorts NULL last, SQLite sorts it first, so every running total shifts. Both engines load in your browser (about 4 MB, once). Nothing is sent anywhere.

  1. Read the code. The quiz gives you CREATE TABLE and INSERT statements. Turn them into a grid and circle every NULL and duplicate row.
  2. Trace in order. FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY. Write down the rows that survive each step.
  3. Answer twice. Write the output for both engines, or "error", or "sqlite3 and postgres are the same".

 * It is deliberately simplified so that every row can be read
 * and every query can be calculated by hand.
 */

-- stores the "name" of the terminal that "owns" the conversation

    sid INT,
    name TEXT
);

/* A message is one round of a conversation: a prompt and the reply it got.
 *
 * mid       the message's id; it sorts in the order the turns happened

    mid INT,
    prev_mid INT,
    sid INT,
    model_id TEXT,
    user1 TEXT,
    response TEXT
);

    model_id TEXT,

);

Postgres vs SQLite

Postgres is strict: real types, errors on anything ambiguous, NULL sorts last. SQLite is forgiving: loose types, guesses instead of erroring, NULL sorts first. Almost every quiz answer that differs between the engines comes from one row of this table. Pick a row to run its example below.

The same on both engines: NULL logic (NULL = NULL is NULL), aggregates skipping NULLs, join counts, set operations treating NULLs as equal, NOT IN returning nothing when the list holds a NULL, and recursive CTEs. How each line of a query runs

A query is written SELECT-first but runs FROM-first. Step through it and watch which rows survive each clause. This is exactly how you trace his problems by hand.

NULL poisons everything

  • Any operator on NULL returns NULL, including NULL = NULL. Test with IS NULL.
  • WHERE keeps a row only when the condition is TRUE. NULL counts as "not TRUE", so the row is dropped.

Practice: Unfinished Parts (DataLemur), 584. Find Customer Referee (LeetCode, the classic <> 2 NULL trap)

Aggregates skip NULLs, count(*) doesn't

With two arguments, max and min aren't aggregates. See the Postgres vs SQLite table above.

Practice: Cards Issued Difference, 1148. Article Views I

CASE and COALESCE

  • A CASE with no matching branch and no ELSE returns NULL.
  • CASE inside an aggregate is the most common interview pattern: turn each row into 1 or 0, then sum.
  • COALESCE(a, b, ...) returns the first argument that isn't NULL.

Practice: Laptop vs. Mobile Viewership, Final Account Balance, 610. Triangle Judgement, 1211. Queries Quality and Percentage

LIKE vs ILIKE

The fruit names are capitalized, so case sensitivity decides the count.

Practice: 1527. Patients With a Condition

GROUP BY, WHERE vs HAVING

  • NULL forms its own group.
  • WHERE filters rows before grouping and can't contain aggregates. HAVING filters groups after grouping and can.

Practice: Data Science Skills, Duplicate Job Listings, 570. Managers with at Least 5 Direct Reports

Joins are a cross join plus a filter

Every join starts as a cross join (every row paired with every row) and keeps the pairs where the condition is TRUE. To count by hand: for each key value, multiply left count by right count, then add. NULL keys contribute nothing. Hover or tab to a row to see its partners, then switch join types.

Practice: Cities With Completed Trades, Well Paid Employees, 3-Topping Pizzas, 181. Employees Earning More Than Their Managers, 1280. Students and Examinations

Window functions (his Problem 4 was lag)

  • A window function computes an aggregate over a frame of rows and returns it for every row, without collapsing rows like GROUP BY.
  • OVER () is the whole table. PARTITION BY works like GROUP BY inside the frame.
  • ORDER BY inside OVER makes a running frame. The default (RANGE) includes tied rows together. ROWS UNBOUNDED PRECEDING gives a strict row-by-row prefix.
  • Because NULL sorts at opposite ends, nearly every window query on id differs between the engines.

Practice: User's Third Transaction, Top Three Salaries, Tweets' Rolling Averages, 178. Rank Scores, 1204. Last Person to Fit in the Bus

Views, CTEs and functions

A SQL function is global and takes parameters, a VIEW is global without parameters, and a CTE is local to one statement. A view is pasted into your query every time it runs, so it never makes anything faster.

Practice: 177. Nth Highest Salary (write a Postgres SQL function)

Subqueries

  • A subquery in FROM must be given a name: FROM (SELECT ...) t.
  • A subquery used as a single value must return one row. When it returns more, Postgres errors and SQLite quietly takes the first row.
  • Adding DISTINCT inside an IN (subquery) never changes the result.

Practice: Histogram of Tweets, Second Highest Salary, Supercloud Customer, 176. Second Highest Salary, 550. Game Play Analysis IV

Set operations stack results vertically

  • UNION ALL concatenates. UNION, INTERSECT and EXCEPT also remove duplicates, and here two NULLs count as duplicates.
  • Column names come from the first query. Postgres requires the types to match; SQLite doesn't.

Practice: Spotify Streaming History, 1907. Count Salary Categories, 1341. Movie Rating

Outer joins: the inner join plus the unmatched rows

LEFT JOIN keeps every left row; rows with no partner get NULLs on the right. RIGHT JOIN is LEFT JOIN with the tables swapped, and FULL JOIN keeps unmatched rows from both sides. Switch between them on session and message, the shape of his notes.

Practice: Signup Activation Rate, IBM db2 Product Analytics, 1378. Replace Employee ID, 1934. Confirmation Rate, 1251. Average Selling Price

Anti-joins: NOT IN vs LEFT JOIN ... IS NULL

Both ask "which sessions have no messages?", but NULLs make them disagree. This is the most-tested trap in Quiz 2: his Problems 2 and 3 are these two queries. Step through each session row.

Rule: if the list inside NOT IN (...) contains a single NULL, the query returns nothing. LEFT JOIN + IS NULL and NOT EXISTS treat a NULL key as "no match" instead.

Practice: Page With No Likes, 183. Customers Who Never Order, 1581. Customer Who Visited but Did Not Make Any Transactions, 577. Employee Bonus

Recursive CTEs: walking the conversation tree

A recursive CTE has a seed query, then UNION or UNION ALL, then a query that joins the table to the CTE itself. Each round joins only against the rows the previous round added, and it stops when a round adds nothing. Pick a seed and step through the rounds.

Practice: DataLemur has no free recursive problem, and LeetCode's recursive CTE problems are Premium. Work through quiz2/recursive_cte.sql here instead. The closest free warm-up is Senior Managers (two levels of self join).

Not on the quiz but on the homework: arrays and unnest (Postgres only), and GROUPING SETS / ROLLUP / CUBE.

Quiz 3: bytes per row

The quiz gives two CREATE TABLEs (reorder the columns to use the least space) and two INSERTs (state the bytes per row), answered for both engines. You may use a computer and a database during it. Edit the columns below and the layout recomputes.

  • Postgres: a 23-byte header, plus a null bitmap only if the row contains a NULL (1 bit per column, rounded up to whole bytes), padded to a multiple of 8. Then each non-NULL value starts at a multiple of its alignment. NULLs take 0 bytes. The row is padded to a multiple of 8.
  • SQLite: 1 byte for the header length, 1 byte per column for its type code, then the values with no padding. NULL, 0 and 1 take 0 body bytes. Small integers shrink to 1, 2, 3, 4, 6 or 8 bytes. A whole-number real in a REAL column is stored as an integer.

"Check in real Postgres" builds the table in the in-browser Postgres and asks pg_column_size, which reports header + data before the final padding.

Rest of Topic 06, short-answer level

  • Normalization splits data into tables linked by keys so each fact is stored once. Denormalization merges them, trading redundancy for fewer joins. He talks about "more or less normalized", not numbered normal forms.
  • Constraints: NOT NULL, UNIQUE, CHECK, PRIMARY KEY (UNIQUE NOT NULL), REFERENCES (foreign key). In pagila, payment.rental_id UNIQUE REFERENCES rental means every payment has a rental and each rental has at most one payment.
  • TOAST: values over about 2 KB are compressed or moved to a hidden side table, leaving a pointer in the row.

Quiz-day checklist

Run through this for every problem before writing "sqlite3 and postgres are the same".

  • Did any NULL get sorted? Postgres puts it last, SQLite first, and that ripples into GROUP BY output and every window function.
  • LIKE: case-sensitive in Postgres, case-insensitive in SQLite. ILIKE is an error in SQLite.
  • Do the types match across a UNION, or in a comparison? Postgres errors; SQLite carries on.
  • Does a single-value subquery return more than one row? Postgres errors; SQLite uses the first.
  • NOT IN over a list containing NULL returns nothing, on both engines.
  • NULL never matches in a join, but UNION, INTERSECT, EXCEPT, DISTINCT and GROUP BY treat NULLs as equal.
  • count(*) counts NULL rows; count(col) doesn't.
  • Join count = the sum over each key of (left count × right count). Duplicates multiply.
  • A window ORDER BY defaults to RANGE, which includes tied rows; ROWS doesn't.
  • A recursive CTE seeded on a duplicated row walks once per copy with UNION ALL, once with UNION.
